# Paperboat launch checklist

The **only** progress tracker. PLAN.md explains each item (decisions, scope, where to start);
this file records whether it works. Work top to bottom, one section at a time: a feature is
done when **all** its scenario rows and command rows are `[x]` on L, M and W. Then the next.

## How to mark

- Cells: **L** = Linux (hp), **M** = macOS (apple), **W** = Windows (victus). For S-sections
  (groundwork, infrastructure, release) only the first cell is used.
- `[ ]` not verified · `[~]` in progress · `[x]` verified on the real device · `[!]` fails
  (write the failure in Evidence) · `n/a` impossible on that platform (say why in Evidence).
- Mark `[x]` **only** with evidence: a smoke-suite test id with its results file
  (`smoke:<id> results/<file>.json`), or the commit plus exact command and result summary
  for a manual check (`manual: <commit> <what was run> → <result>`).
- When a fix changes code, re-verify every `[x]` row of the affected features on all
  platforms; any row that breaks becomes `[!]` and is fixed first (regressions first).
- Commit and push this file together with the work it records.

## Command rows: what `[x]` means

A command row is `[x]` on a platform only when, on that platform: (1) its main use works
against real machines and server with a correct result; (2) every flag in
`cli/docs/cli/<command>.md` behaves as documented (or the doc is fixed); (3) `--json` output,
where supported, is valid; (4) errors are clear for invalid input, missing permission, target
offline and not signed in; (5) `--help` is accurate; (6) it is in the smoke suite when it can
be automated. Hidden/internal commands (e.g. `pb daemon …`) are verified through the flows
that use them; say which in Evidence.
