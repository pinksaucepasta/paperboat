Oracle-hop bias: ssh path is winpool-1 -> oracle public IP -> 127.0.0.1:12211 L-tunnel -> hp:22 (one extra TCP forward + one extra ssh -L hop vs pb peer-to-peer/relay). Prior latency work (results/SUMMARY.txt) shows ssh p50 ~447ms vs pb p50 ~247ms (+200ms) from this hop + ssh overhead. For the flood case the bias is negligible next to the 60s-vs-1s gap: the extra ~0.2-0.4s RTT cannot explain ssh never stopping. If anything the hop flatters pb (ssh numbers are slightly inflated), yet pb still stops ~60x sooner with the paste, and ssh is faster only in the nopaste baseline where no backlog blocks the 0x03.

Result: pb is NOT slower than plain ssh under the specified flood (paste+yes+stalled viewer). pb stops in 0.6-1.4s and the shell answers; plain ssh never stops within 60s (50-56MB still flowing, shell never answers because the driver gives up before asking). Per task, no host fanout/discard / client hold / ConPTY read-size delay analysis required.

Notes: ssh path has one extra oracle hop (+~200 ms baseline typing latency, negligible against 60 s). Plain ssh without the paste also stops (1.66 s); the 256 KiB paste queues the 0x03 behind data the flooding yes never reads. Driver stays in scratch (not committed); the committed pb-only check is cli/internal/hostruntime/pty TestDeviceClientCtrlCUnderFlood (bound 5 s).
