Fixed build: dev-1347c7c54f (client-only commit: an ack records its region, unanswered handshakes probe the other relays; the code is identical to the pushed commit, which only adds a test change).
Old build: dev-ea326e98da. Target: winpool-8 (Windows, build F, machine_75b64781).

3. Both callers exec the runner every ~2 s for 150 s.

## Result
- Fixed caller: 28/28 succeeded. The first took 9.0 s, during the runner's service restart; every later one took ~3 s.
- Old caller: failed exec_start_uncertain 3 times in a row (31 s each) from 06:13:02, when its remembered relay for the runner went stale.
- Old caller in step 1: could not reach the other container (exec_start_uncertain, 31.5 s). The fixed caller reached the old one in 2.7 s.

## Earlier runs (same day, kept as controls)
- With direct UDP open, both callers kept working; the data path was direct, so the relay was not needed.
- Callers that only ever dial the runner also healed: regional recovery stays bound to the last successfully dialed pair and re-promotes its relay. That is why hp, which dials many machines, stayed stuck.
