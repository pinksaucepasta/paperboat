FIX-PATHLOSS2: with a lossy direct path held down, the session stays on the relay (2026-11-16 IST)
Machines: winpool-1 (GitHub Windows runner, Azure 132.196.62.242, machine pl2-w) -> pl2-h (container on hp Wi-Fi,
10.0.0.8), one throwaway account. 8 MB random stdin via `pb exec pl2-h -- sh -c 'cat >/dev/null'`, MB/s of wall
time. Loss = hp DOCKER-USER rule dropping 40% of UDP from 132.196.62.242 to 10.0.0.8 (relay traffic untouched);
relay-only = the same rule at 100%. Counters: pcap on pl2-h's veth (hp) and pktmon on Windows (packets > 600 B by
destination; "direct s" = seconds in which Windows sent data to hp's direct address).

Suspect from the brief (ping/call-me-maybe storm while the path is in doubt) measured and ruled out: disco on the
direct path was 40-50 datagrams per ~120 s run each way (~0.4/s), no extra relay bytes (9.3-9.7 MB in for 8 MB in
lossy and relay-only runs alike). Rule S: web search (tailscale magicsock call-me-maybe / lossy direct worse than
DERP) found no upstream report; ref/tailscale wgengine/magicsock/endpoint.go discoPingTimeout clears an untrusted
bestAddr and drops the ping, and heartbeat()/wantFullPingLocked/sendDiscoPingsLocked rate-limit pings per endpoint
(discoPingInterval 5 s), so pings are not the cost.

Real cause (Windows pcap + a local logging build): data still rode the lossy direct path for long stretches (before:
61 of 128 s, 0.02 MB/s while there), and every such stretch collapses the session's congestion window, which then
regrows slowly over the ~0.3 s relay RTT. Three holes in the fork's loss demotion (f3b499e17/22a0c35bd):
1. discoPingTimeout cleared an untrusted bestAddr before recording the lost heartbeat. A heartbeat times out 5 s after
   it was sent, usually after the 6.5 s trust from the previous pong, so most losses never reached the window and
   rediscovery put the path back with no hold-down. Fix 0b04e51f9 (record first; demote at 3 losses without waiting
   for a full window).
2. handleCallMeMaybe / sendPingsLocked deleted hp's endpointState whenever hp's call-me-maybe list changed (Wi-Fi
   NAT), wiping the window and the hold-down (log: "delete 122.176.235.126:41642 handleCallMeMaybe", then "now using"
   the same address 4 s later). 3. After a hold-down, clean heartbeats shifted the old losses out, so the re-promoted
   path rode 38 s until 3 new losses. Fix 8abfc248e: the loss record lives in endpoint.pathLoss (outlives
   endpointState, bounded at 16, cleared on a connectivity change); a path demoted before is dropped on its first lost
   heartbeat until a full clean window.
   Review (Spark): send failures and disco-key cancels counted as loss -> fb5827f6e (only a timeout counts; eviction
   keeps live hold-downs). Prior art: ref/tailscale and ref/netbird keep a path until full timeout / ICE failure.
