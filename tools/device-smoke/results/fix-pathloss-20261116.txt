FIX-PATHLOSS: a direct UDP path that loses a third or more of its packets is dropped for the relay (2026-11-16 IST)
Cause: magicsock keeps bestAddr while any heartbeat pong lands within trustUDPAddrDuration (6.5 s) and betterAddr
compares latency only; nothing counts loss. Upstream Tailscale has the same rule (ref/tailscale
wgengine/magicsock/endpoint.go handlePongConnLocked, discoPingTimeout); a path losing half its packets answers
enough pongs to stay preferred over a clean relay.
Fix (fork pinksaucepasta/tailscale f3b499e17 + 22a0c35bd): heartbeats to bestAddr fill a 10-probe window per
address; a lost heartbeat with 3+ losses in the window demotes it (next candidate, else DERP/peer relay) and keeps its
pongs from re-promoting it for 30 s, doubling per demotion in a row up to 8 min. The window survives the demotion,
so a path promoted again after the hold-down is dropped on its first lost heartbeat; a recovered path's clean
probes shift the losses out, and a loss-free window resets the doubling. Prior art: none of ref/tailscale
(magicsock), ref/netbird (client/internal/peer conn.go, worker_ice.go, worker_relay.go) demotes on partial loss;
they only drop a path on full timeout / ICE failure.
Machines: two throwaway Linux containers on pbvm2 (plos-a, later plos-c, caller, plos-b target, one account, docker bridge, direct
path 172.17.0.9 <-> 172.17.0.12). Loss = iptables in plos-b dropping 40% of UDP from plos-a's address at random
(only the direct path; the relay's address is untouched). Data: 8 MB /dev/urandom as `pb exec plos-b -- sh -c
'cat >/dev/null'` stdin. Before: path from `pb ping plos-b --json`. After: bytes that reached plos-b per source
address during the transfer (tcpdump on plos-b's veth), because `pb ping` reports a direct path whenever a direct
disco ping answers, even while data rides the relay. 172.17.0.17 = direct (plos-c), 49.36.124.90 = direct via the
NAT hairpin (pbvm2's public address), 152.67.0.60 / 140.245.11.41 / 157.180.74.88 = Paperboat relays.
pbvm2 sits on a mobile hotspot today (power cut), which caps every relay run at 0.5-1.9 MB/s.

Result: a 40%-lossy direct path no longer carries the session: it moves to a clean candidate or the relay within
one 30 s window, re-probes cost one lost heartbeat each, and the clean path returns once loss stops. Over this
hotspot the relay itself is only 0.55 MB/s, so lossy-after (0.4) is close to the relay ceiling, not above the
before numbers; the throughput gain shows where the relay is faster than the lossy path (Windows runner -> hp:
relay 2.05 vs lossy direct 0.06-0.31 MB/s, fix-execstdin-20261116.txt). That Windows rerun was not done here.
