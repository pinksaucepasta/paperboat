## Why the TLS part is open (staging accounts are `self-hosted-only`, selfhost_pool_policies)
1. `pb tunnel create --from tcp://...` and `pb tunnel list` fail with "paperboat-server returned an unsafe tunnel response" on
   a self-hosted-only account: decoratePublicEndpoints (server/internal/tunnelv1/repository_changes.go:295) returns
   stable_endpoint "" for a tunnel without a bound custom domain, and the CLI (cli/internal/api/tunnel_v1_validate.go:362)
   only accepts "" together with summary_code custom_domain_required, which the server sets only for tunnels with an
   http/tls route. A TCP-only tunnel gets summary "pending". The tunnel exists on the server; the CLI errors after create.
   Workaround used: create an http tunnel first, bind a verified domain (`pb tunnel domain add`), then `route add --protocol tcp`.
2. `pb tunnel route add --protocol tls` fails with invalid_request once a custom domain is bound: the CLI sends the
   decorated (custom) hostname, the server compares it with the raw managed stable_endpoint
   (server/internal/tunnelv1/resources_repository.go:528-531, route-add loads the undecorated row). A tls route created by
   raw API with the managed hostname (after removing the default http route) stays `custom_domain_required` /
   connector_pending, and a TLS handshake to the edge with that route's SNI ends in an internal-error alert, with the
   bound custom domain's SNI in an EOF. Not diagnosed further.
3. tcp1/obs1 of the REL-EDGE account show the same state, so `pb tunnel list` is unusable on that account.

Also seen: pb-rel-edge-1/-2 log `tunnel_certificate_distribution_failed` every 5 s (staging certificate distribution);
`pb tunnel domain add --wait` ends in tunnel_operation_wait_timeout on staging.
